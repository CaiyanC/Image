# 统一工具平台设计

## 目标

将现有 AI 图像/视频生成系统演进为统一企业工具平台。开发人员将已开发的内部 Web 工具登记到平台；使用者登录后只看到自己所属部门被授予权限的工具。首个接入工具是财务部使用的“电商数据自动填表助手”，保留其电商数据分析表、周月报和亚马逊库存三个流程。

## 范围

本期同时交付平台底座和首个工具接入：

- 工具中心：所有已登录用户的默认首页，按当前用户权限展示可访问的工具卡片。
- 工具管理：仅总经办和 IT 部可登记、编辑、启停和排序已开发的内部工具。
- 工具注册与权限：工具只能指向已发布的前端页面和已实现的后端服务；不能上传、执行或配置任意 EXE、脚本或 URL。
- 首个工具：将 v1.0.35 对应的 Python 填表源码接入后端后台任务；财务部、总经办和 IT 部可使用。
- 任务与文件：上传 Excel、后台运行、查询状态、下载结果和审计记录。

本期不包含：从网页上传插件包、第三方工具市场、部门级产品/SKU 行级数据隔离、移动端专用交互，或对已有 AI/产品业务规则的重写。

## 现有基础与版本基线

现有系统已有用户—部门—权限点 RBAC：用户可属于多个部门，部门绑定权限，前端基于权限显示导航并保护路由，后端以 `require_permission(...)` 强制接口授权。已有财务部、总经办和 IT 部部门定义；总经办和 IT 部拥有管理权限。

`C:\Users\wnt\Desktop\测试7_23\EcommerceDataFillTool_v1.0.35` 是版本号 `1.0.35` 的 Windows 打包 EXE，仅用于现有行为对照。平台集成使用 `C:\Users\wnt\Desktop\电商数据分析表自动填写工具` 中同版本 Python 源码，不在服务器上调用 EXE 或 Tkinter GUI。

## 方案选择

采用“受控内部工具注册”方案：开发人员先实现前端页面、后端 API 和任务处理器，再由总经办/IT 部在工具管理中登记元数据并绑定既有权限点。

没有采用以下方案：

- 静态前端配置：实现最快，但每新增工具都要改导航代码，不能满足平台化管理。
- 上传 EXE/脚本作为插件：会让服务器执行未经审核的代码，无法满足权限、安全、审计和部署稳定性要求。

## 架构

```text
开发工具代码 ──> 受控工具注册 ──> 工具中心卡片 ──> 受权限保护的工具页/API
                                 \
                                  └─> 文件型工具任务 ──> Celery ──> 安全结果下载
```

### 工具目录

新增 `Tool` 数据实体，字段为：

- `tool_key`：不可变、唯一的代码标识，例如 `ecommerce_data_fill`。
- `name`、`description`、`category`、`icon_key`：用户可见的展示信息。
- `route_path`：内部前端路由；必须在应用允许的 `/tools/` 前缀下，且与代码注册路由匹配。
- `permission_key`：使用该工具所需的既有或新增权限点。
- `is_enabled`、`sort_order`：管理端控制的启停与排序字段。
- `created_at`、`updated_at`：审计辅助字段。

工具中心只返回同时满足“已启用”和“当前用户拥有 `permission_key`”的工具。管理端能看到所有工具，但不能创建任意执行入口；后端对 `tool_key`、`route_path` 和 `permission_key` 做白名单验证。

### 权限

新增权限点：

- `tool.manage`：管理工具目录；仅总经办、IT 部。
- `finance.ecommerce_data_fill`：使用电商数据自动填表工具；授予财务部、总经办、IT 部。

现有业务页面的权限保持不变。工具中心的工具卡片、工具详情页、创建任务接口、查询任务接口和下载接口都复用同一 `finance.ecommerce_data_fill` 权限，并额外校验任务所有者；管理组可审计所有任务。

### 首个工具：电商数据自动填表助手

该工具的网页入口为 `/tools/ecommerce-data-fill`，保留三个模式：

1. 电商数据分析表填写；
2. 周月报填写；
3. 亚马逊库存表填写。

网页取代 Tkinter 的文件选择界面：用户选择模式、上传该模式所需 Excel 文件、填写当前源码已有的周期/日期参数、确认文件识别结果并提交。后端调用同版本源码中已有的 `run_ecommerce_fill(...)`、`run_kepule_fill(...)` 或 `run_amazon_inventory_fill(...)`，输出文件名、异常清单、人工复核报告和运行日志保持与 v1.0.35 的业务语义一致。

为避免 `src` 通用模块名与平台代码冲突，填表源码以独立的后端内部包导入；Tkinter、拖放和桌面路径模块不进入运行时依赖。现有工具项目的测试样例与输出文件用于集成回归测试。

### 任务、文件与审计

新增通用 `ToolRun` 实体，供本期和未来文件型工具共享：

- 关联 `tool_key`、创建用户、状态、参数 JSON、输入文件清单、输出文件清单、失败摘要及开始/结束时间。
- 状态为 `queued`、`running`、`succeeded`、`failed`。
- 上传文件保存至 `uploads_dev/tool-runs/<run-id>/input/`（生产为 `uploads/tool-runs/...`）；输出保存到同一运行目录的 `output/`。使用 UUID 文件名，原文件名仅作为显示元数据。
- 仅接受 `.xlsx`；API 在读取文件头前限制数量和单文件大小，并拒绝路径、重复扩展名和不合法工作簿。
- 任务通过现有 Celery 队列执行；API 不直接运行 Excel 处理。
- 下载通过受鉴权的工具文件接口返回，不复用对所有用户开放的静态路径；任务发起人可下载自己的文件，管理组可下载所有文件。
- 记录创建、完成、失败和下载操作日志。运行目录保留策略作为配置项，默认不自动删除历史数据，避免在未确认保留周期前误删财务文件。

## 前端体验

登录成功后，若用户有任何已启用工具，跳转 `/tools`。没有任何工具权限的用户进入现有“无访问权限”页。

工具中心显示分类、工具名称、说明和进入按钮；不显示无权工具。已有 AI 创作、智能客服、产品和素材库仍保留原有入口与权限，本期将它们作为内置工具登记到工具中心，使用户可以从一个统一入口进入。原有直达路由继续有效，防止已有书签和链接失效。

工具管理页放入现有“管理”菜单，提供：新增内置工具、编辑展示信息、选择允许的预先注册路由与权限、启停、排序和查看最近运行记录。管理端不能输入外部地址、命令行或脚本路径。

电商填表页采用模式选择、文件上传、参数填写、提交、轮询任务状态、结果下载的顺序；失败时展示可读错误摘要，成功时显示输出列表和建议人工复核提示。

## API 边界

- `GET /api/tools`：当前用户的可用工具列表。
- `GET /api/admin/tools`、`POST /api/admin/tools`、`PUT /api/admin/tools/{tool_key}`：管理端工具目录；要求 `tool.manage`。
- `POST /api/tools/ecommerce-data-fill/runs`：上传并创建填表任务；要求 `finance.ecommerce_data_fill`。
- `GET /api/tools/ecommerce-data-fill/runs`：当前用户任务列表；管理端可按用户筛选。
- `GET /api/tools/ecommerce-data-fill/runs/{run_id}`：任务详情；仅所有者或管理端。
- `GET /api/tools/ecommerce-data-fill/runs/{run_id}/files/{file_id}`：受鉴权下载；仅所有者或管理端。

所有创建和下载接口写操作日志，所有查询与下载都验证工具权限、任务归属和文件路径归属。

## 数据迁移与初始化

使用 Alembic 新建迁移创建 `tools` 与 `tool_runs` 表，并在启动种子中确保新增权限、默认权限分配和内置工具注册幂等执行。迁移不得修改或删除现有用户、部门、权限、产品和 AI 生成数据。

默认注册的内置工具包括：AI 创作、智能客服、产品管理、素材库和电商数据自动填表。它们仅引用当前已有受保护路由或本期新增路由。

## 测试与验收

后端测试覆盖：工具目录可见性、管理权限、非法路由/权限拒绝、工具启停、财务部创建任务、其他部门拒绝、所有者隔离、管理端审计、文件路径隔离、Celery 任务状态转换，以及三种填表模式对固定样例的输出文件清单和关键单元格结果。

前端测试或构建验收覆盖：登录跳转工具中心、工具卡片按权限显示、管理页仅管理组可见、填表页三种模式、上传/提交状态和无权限跳转。保留既有直达页面和既有权限路由的回归验证。

当前基线已知限制：后端完整 `pytest tests -q` 因未跟踪的 `tmp_supplemental_rerun.py` 缺失而在测试收集阶段失败；前端 `npm run lint` 因既有 `AssetLibrary.tsx` 的 ref 规则错误失败，但 `npm run build` 已构建成功。本期不将无关 lint 修复混入功能改造；本功能测试、后端排除该缺失依赖后的回归测试以及前端构建必须通过。

## 发布与回滚

仅在用户明确要求发布时，将已验证的 `dev` 合并到 `master` 并执行生产重启流程。回滚方式是停用电商工具目录记录或回滚本期迁移/代码；停用不会删除历史 `ToolRun` 与财务文件。
