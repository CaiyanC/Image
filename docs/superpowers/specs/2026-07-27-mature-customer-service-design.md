# 成熟智能客服交付收口设计

## 目标

把现有“语义路由 + 字段查询 + 安全拒答”升级为可实际接待产品咨询的智能客服。系统继续由 DeepSeek 理解完整问题、上下文、多意图、比较与推荐；确定性代码只负责实体合同、字段合同、同 SKU 证据、证据有效性、安全边界和最终一致性。

完成后的核心行为是：只要当前问题已经唯一绑定商品，并且该 SKU 的数据库、产品 QA 或文件知识库中存在足以回答的证据，系统就先回答已知部分；只有真实歧义、完全无证据或实时信息无法确认时才澄清或安全说明。

## 当前问题

1. 结构化字段、产品 QA、文件知识库和描述字段仍由不同快捷路径消费，正式字段为空时可能阻断同 SKU QA/RAG。
2. DeepSeek 已识别比较意图和参与商品，但字段、子类型或 JSON 有轻微波动时，后端会整体判为无效并澄清。
3. “有什么区别”“怎么样”“值得留意什么”等正常开放问题可能因缺少单一 canonical field 而被视为信息不足。
4. 多子问题链路会在答案已覆盖某个结论后，再依据词面覆盖检查追加“当前资料未直接确认”，造成自相矛盾。
5. 润色、缺失补充和安全检查分散在多个阶段，没有统一终稿裁决。

## 方案选择

采用增量中央重构，不重写数据库模型、API 或现有实体/字段合同。

- 不采用逐问句或逐 SKU 规则：无法泛化，并会继续造成路由竞争。
- 不采用一次性重写客服主服务：当前已验证能力多，整体替换风险过高。
- 采用新的小型中央组件，逐步让比较、QA、开放 RAG 和多轮消费统一接口；旧快捷路径在等价能力接入后再删除。

## 架构

### 1. `CustomerEvidenceBundle`

为一个 canonical SKU 聚合客户可见证据：

- 产品身份；
- 正式结构化字段；
- 同 SKU 产品 QA；
- 中文/英文标题与描述；
- 五点描述、卖点、场景等客户内容；
- 同 SKU 文件知识库片段；
- 每条证据的来源、字段、有效性与冲突状态。

聚合层不理解问题、不选择商品、不生成答案。它只在既有 `EntityResolutionContract` 允许后读取该 SKU，并应用客户可见字段白名单。

### 2. `AnswerCoverageContract`

把当前问题拆成语义请求单元，每个单元记录：

- `request_id`
- `request_text`
- `intent_kind`
- `canonical_fields`
- `evidence_requirements`
- `status`: `answered | partially_answered | unsupported | ambiguous`
- `supporting_evidence_ids`

覆盖状态由语义计划和真实证据共同决定，不能通过答案词面是否包含原问题来判断。

### 3. 渐进式回答策略

按以下顺序裁决：

1. 完整证据：完整回答；
2. 部分证据：回答已知部分，仅对真正未覆盖单元说明边界；
3. 开放产品问题：从同 SKU 证据中生成综合概览；
4. 比较未指定维度：默认生成结构化综合比较；
5. 实体真实歧义：列候选澄清；
6. 完全没有同 SKU 证据：安全缺失。

“未指定比较维度”不是澄清条件。只有用户要求系统替其做最终选择，而决定所需条件确实缺失时，才在先给出已知比较后追问偏好。

### 4. DeepSeek 计划容错

语义计划验证采取“保留可靠部分”的方式：

- 已验证的两个实体和 comparison 意图不能因 subtype 或 field 缺失而丢弃；
- 单字段明确时执行字段比较；
- 多字段明确时执行多字段比较；
- 未给字段时执行综合比较；
- 非标准但可映射的 canonical field 进入 allowlist 适配；
- 无法唯一绑定实体时仍保持原有安全澄清。

容错代码不从关键词重新推断意图，也不选择 SKU。

### 5. 统一终稿裁决

所有生成、缺失说明和润色完成后执行一次中央审查：

- 每个请求单元的回答覆盖；
- 所有事实是否由绑定 SKU 的证据支持；
- 是否存在跨 SKU；
- 是否存在已回答后又声明无法确认；
- 是否存在重复、空泛尾巴或内部术语；
- 润色是否改变事实。

终稿裁决可以删除由旧覆盖检查错误追加的缺失句，但不能删除真实的证据边界。

## 数据流

```text
完整问题 + 会话上下文
→ DeepSeek semantic preplan
→ FieldContract / product_qa contract / comparison contract
→ EntityResolutionContract
→ canonical SKU(s)
→ CustomerEvidenceBundle(s)
→ evidence selection
→ AnswerCoverageContract
→ grounded generation
→ final answer arbitration
→ factuality verification
→ customer-friendly polish
→ final consistency verification
```

## 安全边界

- 不允许无实体合同输出商品事实。
- 不允许跨 SKU 证据。
- 不开放 INTERNAL_ONLY 和 EVIDENCE_ONLY 字段。
- 实时库存、价格、优惠、物流时效只在有可靠实时来源时回答。
- 数据冲突不能静默选择，必须说明可核验边界。
- 不新增商品名、SKU、固定问句、关键词路由或正则特判。

## 验证

每项中央改动采用最小失败测试、邻接合同测试和未参与修复的 UTF-8 真实 HTTP 问题验证。

发布门禁至少包括：

- 明确 SKU、完整名称和唯一简称的字段问答；
- QA 原问与自然改写；
- 文件知识库和开放 RAG；
- 单字段、多字段和无指定维度比较；
- 多子问题部分覆盖；
- 歧义、未知商品、缺失和实时信息；
- 多轮、代词与会话隔离；
- 推荐候选身份与同 SKU 条件证据；
- 人工阅读完整答案。

以下指标必须为零：错 SKU、错字段、跨 SKU 证据、有效同 SKU 证据却回答缺失、无理由澄清、已回答后追加矛盾缺失、空回答和未分类 REVIEW。
